## 3. 性能与稳定性问题清单

### R01 · P1：拍照前及进入图库时同步处理整个照片索引

**源码确认。** `PhotoCaptureService.kt:145–149` 在 `onCreate()` 恢复索引；`:288–300` 在主线程准备文件并调用 `markPending()`。`PhotoRepository.kt:60–79、111–135` 读取完整 JSON、重写完整索引；`complete()` 还对全部记录排序。`RecentPhotosScreen.kt:65、104、115` 在初次组合、返回和刷新回调同步读索引。

`Navigation.kt:61–64` 会绑定照片服务，`PhotoCaptureModel.kt:49–61` 使用 BIND_AUTO_CREATE，因此即使用户只进入首页，照片仓库恢复也可能发生。主线程还可能等待同一 repository 的 IO 线程持有的同步锁。

影响：照片越多，点击到实际调用相机、首页进入和图库返回越可能变慢；慢磁盘可能放大为 ANR 风险。没有实测毫秒数。

修复：建立单一仓库写入入口，在 IO dispatcher 执行恢复/读写；页面订阅快照；将长列表改为分页，后续用事务数据库或增量日志避免每张照片全量重写。不得只把同步锁搬到后台而继续让主线程等待。

验收：0/50/1,000/10,000 条记录，StrictMode 无这些调用点的主线程磁盘读写；索引规模增长不拖慢快门受理。

### R02 · P1：首页、文件导出和设置导入存在主线程阻塞/异常路径

**源码确认。** `StartRecording.kt:134` 直接在组合中调用 `lastRecording.hasRecordingsAvailable()`，经过 `AppSettings.kt:178–184` 进入 `BatchesFolder.kt:335–362` 的文件枚举/ContentResolver 查询。

`ui/utils/file.kt:26–38` 在 ActivityResult 回调中同步复制整个文件，没有 IO 切换和异常处理；大视频或慢 SAF provider 可长时间阻塞 UI，授权撤销/写满可能抛异常。用户取消也执行 `callback(null)`，而 `RecorderEventsHandler.kt:63–92` 的回调在启用立即删除时并未先检查导出成功，存在取消导出仍清理录制片段的风险。

`ImportExport.kt:57–65` 在回调中复制、读取并反序列化导入文件，包含强制非空、未关闭的输出流表达式，缺少大小限制和失败反馈。

修复：所有扫描/复制/解析进入 IO；导出结果明确区分成功、取消、失败，仅成功后执行清理；限制导入大小并校验设置范围；使用 `use` 关闭两端流，失败保留源文件。首页使用缓存和显式失效刷新。

验收：取消导出、损坏 JSON、失效 URI、空间不足、慢 provider、大文件复制均不冻结界面、不删除未导出的源片段，错误可恢复。

### R03 · P1：照片启动/停止/保存缺少完整的会话隔离

**源码确认，交错时序待复现。** `PhotoCaptureService.kt:485–578` 初始化协程等待 provider 后未复核 session ID、停止状态就绑定相机并发布 READY。服务被 UI 持续绑定时，`stopSelf()` 不等同于立刻销毁对象/取消 scope。

`:411–415` 创建 5 秒停止协程但不保存或取消 Job。会话提前收尾后若立刻开始新会话，旧定时器可能调用 `finalizeStop()` 停掉新会话。`:637–703` 保存 worker 也缺少代际检查；旧 IO 完成后可能写入新会话共享状态，`catch(Throwable)` 还会把取消当作普通错误。相机回调在检查 session ID 前就修改 `captureInFlight`，错误回调还会清空队列。

修复：为初始化、停止计时器和保存 worker 明确 Job 所有权；使用会话 ID/代际 token，先校验再改状态；新会话启动前取消旧控制任务。保存数据的收尾策略需与 UI 会话分开，保留可恢复记录；重新抛出 CancellationException。

验收：人为延迟 provider/保存，连续执行启动→停止→重启；旧回调不得改变新状态、解绑新相机或清空新队列；停止后不再次出现 READY 或悬浮窗。

### R04 · P1：仅曝光队列有上限，保存积压没有背压

**源码确认。** `PhotoCaptureService.kt:230–237` 只检查 `captureQueue.size >= 8`；`:327–336` 每次曝光成功加入 `saveQueue` 后立即拍下一张；保存队列无上限/字节预算。状态 SAVING 仍能接受快门。慢外部保存下，曝光队列即使不满，临时 JPEG 仍可能不断积累。队列储存的是文件描述信息，不能直接把它描述成“整张 Bitmap 堆积导致 OOM”。

修复：对曝光中、等待曝光、待保存、保存中建立统一未完成请求预算及临时磁盘预算；满载给区别于受理成功的反馈；错误暂停受理；失败请求采用集合而非只保留最后一个 `failedSave`。

验收：限制保存吞吐后连续点击，积压始终有界；每个已受理请求都有成功/失败/中断记录；满载不震动为成功受理。

### R05 · P1：保存提交与恢复不完整

**源码确认。** `PendingPhoto` 只记录临时路径、时间和镜头，没有目的地 URI、名称或提交阶段。`PhotoStorage.storeInternal()` 直接复制到最终名称；MediaStore/SAF 创建输出后没有先把 URI 写入恢复日志。`PhotoRepository.readIndex()` 将任意读取/解析失败当成空索引，下一次写入可能覆盖历史索引。`recoverPendingFiles()` 返回的待恢复文件未进入可操作恢复界面。

影响：中断时可能留下半成品/孤立成品，索引损坏时历史照片可能在列表中消失；这不等于照片文件已经被删除。当前不能宣称已实现完整的持久化事务恢复。

修复：持久化输出阶段与 URI；内部使用临时目标加原子提交（在支持的同文件系统条件下）；索引损坏保留原件并显式错误；启动恢复支持重试保存/导出，不重新曝光。重试不删除已经成功提交的成品。

验收：在目标创建、复制中、复制完成、索引提交四个阶段注入中断；重启后不重复曝光、不覆盖历史、可解释并恢复未完成请求。

### R06 · P1：视频启动失败与快速退出存在崩溃/资源竞争风险

**源码确认。** `VideoRecorderService.kt:56、85–99、132` 的 `_videoFinalizerListener` 在第一轮录制创建后才初始化，启动失败或过早停止却可能直接访问；`:185–210` 初始化协程缺少会话失效校验，provider 获取异常未统一处理；`:216–229` 使用 `unbindAll()`。照片已按用例解绑，视频仍可能影响共享 provider 的其他用例。

`RecorderService`、`IntervalRecorderService` 的计时器和 `VideoRecorderService` 的 job 没有统一 `onDestroy()` 清理。`RecorderEventsHandler` 使用无归属线程/Timer，保存 UI 回调与页面生命周期分离。

修复：初始化状态显式化、幂等停止、nullable finalizer/有界等待；按所属用例解绑；统一生命周期 scope、计时器和回调清理；文件选择器调用回到主线程。注意其中 `runBlocking` 位于显式新线程内，**不能将这处单独判定为主线程 runBlocking**。

验收：开始视频后立即停止/暂停、相机初始化失败、连续音视频/照片切换及销毁重建；无 lateinit 异常、晚到录制启动、计时线程或相机所有权残留。

### R07 · P2：预览透明度跨过零时反复创建 Surface

**实现确认，性能影响待测。** `BlackPhotoScreen.kt:188–212` 仅当透明度 > 0 才创建 AndroidView/PreviewView，回到 0 就移除并断开 SurfaceProvider。来回越过 0 会重建预览；透明度也在组合分支读取，拖动期间会触发该作用域重组。alpha 已在 graphicsLayer 中应用，这是已有的合理做法。

修复：测量后选择页面内稳定保留 PreviewView、短延迟销毁或分离可见性/Surface 生命周期；控制状态读取范围。不能直接承诺保留预览会省电；黑屏后台流水线、TextureView 合成与预览耗电需一起比较。

验收：0↔半透明↔1 往返 50 次，记录首帧显示延迟、帧超时、Surface 数和内存；滑动/双指缩放不误拍，三种状态均能点击拍照。

### R08 · P2：悬浮窗重复刷新及拖动持久化

**源码确认。** 每次 `publish()` 都会触发 overlay 更新；`PhotoOverlayController.updateStatus()` 即使状态相同也创建背景、重启动画；`clampToScreen()` 拖动时每次调用 SharedPreferences.apply。

修复：相同状态跳过更新、复用状态背景；位置只在抬手/停止时持久化，窗口位置按帧合并；保留拖动阈值和点击隔离。

验收：连续拖动 30 秒，持久化次数与拖动完成次数相符；无重复状态动画，快门/长按菜单仍可用。

### R09 · P2：图库重复打开文件和高级设置一次布局较多内容

**源码确认，瓶颈程度待测。** 图库每项先检查可访问性，再两次打开流读取尺寸/缩略图，未见共享图片缓存；“全部”加载完整索引。设置使用 Column + verticalScroll，高级设置 AnimatedVisibility 包裹整组内容。

已有正向措施：图库 LazyColumn 有稳定 key；可访问检查和采样解码位于 IO，没有直接解码整张大图到主线程。

修复：先测滚动和展开；按 record ID + URI 缓存缩略图及可访问状态；分页读取；对确有成本的设置列表改 LazyColumn，避免一次展开整组重测量。不要在没有证据时把所有 Column 都改为 LazyColumn。

### R10 · P2：快速抓拍的耗电、质量和用例组合缺少设备基线

**实现确认，设备表现待测。** 照片绑定 Preview + ImageCapture + 640×480 ImageAnalysis，分析帧直接关闭；快速模式尝试 ZSL、FPS 和 OIS。能力声明不等于所有三用例组合都成功，也不能把 30fps 等同于任何运动场景都清晰。

修复：建立绑定失败降级梯度与 CameraState 错误映射；测量快速模式开/关、全黑/预览、弱光/运动的延迟与画质。评估已有 Preview 时是否仍需 Analysis；移除前必须复测黑屏测光和首拍延迟。

验收：不支持能力或绑定失败时有确定降级/错误；30 分钟会话无持续资源增长，记录温升与能耗，不承诺“移动拍照绝不模糊”。

### 已识别的一致性缺口

1. **颜色**：首页绿/黄和悬浮颜色未按暗色/动态色变化；黑屏纯黑属于功能性例外，应明文定义。告警色需要同时有图标/文字，不能只靠颜色。
2. **排版/布局**：首页 11sp 胶囊、固定宽高操作卡片和单行副标题需要 200% 字体检查。历史要求曾提出三按钮竖排，后续参考首页为横排；计划采用紧凑屏竖排、宽屏自适应，实施前以样例验收布局。
3. **形状**：10/16/18/24/28dp 圆角分散定义，原生悬浮菜单另用 6dp；缺少可复用层级。
4. **动效**：Navigation 首页 1.25 倍、设置 0.8 倍缩放、关于页默认 scaleIn、黑屏 180–220ms、小组件 spring 和悬浮 140ms 各自定义，进退方向和幅度不统一。时间数值本身不证明卡顿，但会产生体感差异。
5. **无障碍**：黑屏原始触摸处理缺少语义快门和退出动作；悬浮菜单依赖长按，缺少相应可访问动作。lint 对 performClick 的警告需人工归类：实际 `handleShutterTouch()` 已调用 `performClick()`，不能据此声称点击完全不支持无障碍。
6. **减少动画**：未见项目级统一策略。不能推断 Compose 完全不遵守系统动画设置；需验证自定义无限脉冲、波形和 View 动画在系统动画缩放为 0 时的实际行为。
7. **文案与真实状态**：首页底部“所有录制文件均加密保存在本地设备”过度概括了内部、媒体、用户目录等路径，照片实现为 JPEG 复制；应按实际目录说明，不把系统存储保护表述为应用逐文件加密。静态“已准备就绪”也需与存储不可用状态协调。
